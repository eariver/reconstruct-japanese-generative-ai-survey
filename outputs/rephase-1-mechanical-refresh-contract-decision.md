## 5. Ordinary failure, external drift and interruption

Choose **guarded restoration for caught failures**, plus an explicitly fail-closed manual-recovery outcome for ambiguous/conflicting/interrupted writes. No full multi-file atomicity promise.

- The wrapper knows every prospective receipt/Gate byte string before replacing it. On an ordinary failure before commit, restore only operation-owned files whose current bytes equal either the captured original or this operation's known written bytes, while the captured HEAD/State/provenance and unchanged dependencies still match. Unknown bytes are never called “our changed Gate.” If safe restoration cannot be established, preserve live bytes + retention + guard and return failure with precise paths/hashes; do not overwrite another writer's work.
- The existing revalidation API must retain ownership of record/State changes. Its current `write_json` and unconditional record-unlink rollback are insufficient for the selected owned-write guarantees. A **narrow correction in that owner** is authorized: exclusive creation of a new record without overwriting a collision; State replacement from known serialized bytes; restoration/removal only while the corresponding current State/record still matches its own written bytes and pre-write basis. If a partial I/O write or changed record cannot be safely classified, keep the evidence and fail explicitly rather than delete unknown bytes. Preserve original exception/error evidence and existing strict post-write validation. No generic transaction manager or schema extension.
- The wrapper checks actual State and record disposition after an API failure; it cannot assume the API rolled everything back. Release the cooperative guard only when exact original live authority has been restored, or after successful commit. Keep retained evidence on failed attempts too. Safe pre-live-write aborts may release their own guard; never delete another operation's guard/temp/history.
- Crash/kill/power-loss recovery is not automated. Retained bytes and an occupied guard identify an incomplete operation. A later normal invocation refuses; reconciliation is an explicit operator task under existing authority, not “copy old State back” or automated adoption of an orphan record. Durability/power-loss atomicity beyond the selected file operations is not claimed.
- Snapshot checks and atomic single-file replacement do not provide global compare-and-swap against noncooperating writers. Tests must cover detected interleavings and refuse conflicting restoration; do not advertise arbitrary concurrent-editor safety. No extra Human approval gate is created.
