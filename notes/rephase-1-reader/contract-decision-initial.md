# B3 implementation boundary decision

2026-09-21 JST. Root design decision for the next isolated repair; **not production authority, adoption, or a repaired candidate**. Current frozen application candidate remains f1 `bf32edf98ba8f605169d7188bbc764de74ee4f6e`. Human-fixed production baseline remains `774dd39a951c9ac3818e83dfffd4c7666efb0a20`.

## Why this is more than one missing field

The current Weekly publisher constructs its reviewed JSON from `spec` headlines/decks/blocks and a small publication subset. Its renderer consumes `data`, `plan`, `spec` and `result`, including generated Claim Boundary blocks. Adding only `frontmatter.lede` would leave independently identified omissions. The generic Gate verifies the reviewed JSON's own bytes but permits that JSON and current primary TeX to describe different content; a new caller-supplied `rendered_sha256` alone would merely restate the claimed relationship.

The new [function experiment](probe-results.json) confirms 10 mutations that change TeX without changing current projection: seven prose categories (cover anchors; frontmatter heading, lede, scope notes; final heading; section label; generated Claim Boundary), display date, temporal boundary, and citation key. The last is a citation/render-identity witness, not another prose field. Two controls already covered by current projection change both hashes. Inputs are synthetic, with one package; these are renderer/projection witnesses, not publication workflows.

## Selected direction

Use **one complete reader-oriented input for Weekly review and rendering**, with deterministic derivation checked independently at both Gate creation and Gate revalidation. Keep a distinct direct-source review route where it is already supported. Do not require two editorial judgments merely to repair one missing relationship.

| Route | Review target | Mechanical acceptance |
|---|---|---|
| Weekly generated structured source | Complete reader input before source materialization, including all emitted prose and citation/temporal semantics | Reconstruct the declared source from that same validated input and fixed renderer contract; compare actual bytes and identities |
| Existing direct-primary path, including eligible Special/manual flows | The actual named primary source bytes, with supporting-surface scope explicit | Require the validated review's path/hash to match the actual primary source in the manifest/report; do not accept unrelated JSON |
| Unrelated/legacy partial JSON | No inferred derivation | Reject as new source authority until regenerated/reviewed under a supported route; preserve history |

This is a proposed reconstruction contract. LONGFORM_SPECIAL currently has no demonstrated Weekly-style pre-TeX producer. Do not force its renderer through Weekly fields, infer Special pre-TeX coverage, or announce complete Special/manual support from the existence of a generic Gate option. The route discriminant must come from validated payload shape/contract, never a permissive arbitrary executable or self-asserted success flag.

## Concrete implementation obligations

1. Replace the publisher's partial field projection with a canonical reader input. Cover issue/title/date/window, cover headline/deck/anchors, front heading/lede/scope notes, approved section labels, **rendered result** headline/deck/all blocks including Claim Boundaries, final-summary heading/paragraphs, and citation identities/order. Preserve publication ordering and existing research/architecture checks. Synthesis or audit prose that is not emitted is not automatically a reader field.
2. Render all variable primary-source reader content from that canonical input. Avoid parallel authoring inputs that can disagree after review. The existing `--materialize-surface-only` boundary remains before source files are written. Existing independent semantic judgment remains mandatory; the builder never synthesizes PASS.
3. Separate semantic content from restricted generation/provenance data. The current renderer hashes the full Draft result into a TeX comment. An internal annotation can therefore change exact source bytes while leaving prose identical. Such non-reader inputs may influence only explicitly constrained comments/structure and must be checked through existing source/build authority, not exposed as unconstrained TeX injection. Compare exact generated bytes; do not “solve” this by stripping arbitrary TeX comments/macros or by substring matching reader sentences.
4. Define and test the bibliography/style/supporting-file boundary before claiming whole-reader coverage. Citation target metadata can change meaning without changing body wording; styles and supporting TeX can also emit content. Bind their validated source closure and state precisely what the semantic review covers. The current primary-only experiment does not select or prove a complete supporting-source design. Use existing manifest/provenance responsibilities where sufficient; do not create another independent ledger or dashboard by default.
5. At Gate creation, validate the review record, route, issue/Profile identity, exact input bytes and the declared primary-source relationship. At Gate revalidation, recompute that same relationship from authoritative files rather than trusting an earlier PASS/digest. Explicit `structured_surface_path` must agree with the review's target; stale but individually hash-valid documents must fail.
6. Bind the renderer contract/version to the generated-source route. Later Core changes must trigger the existing reviewed-Core-change/impact/revalidation rules. Do not silently accept a new renderer under a historical review or force unchanged semantic content through gratuitous new editorial review; define the affected responsibility from actual change impact.
7. Preserve existing reviews and released editions as historical evidence. No in-place rewriting of their hashes, decisions or State. Fresh execution is the default trial. A stricter new Gate is not proof that historically released editions were invalid.

## Rejected shortcuts and cost evidence

- A lede-only patch leaves known emitted fields and the JSON/TeX relation unresolved.
- Merely putting an output hash into JSON or manifest proves asserted equality, not derivation from reviewed content.
- Requiring a second direct-TeX review for every already-reviewed generated input duplicates editorial judgment. It is not a demonstrated saving.
- Serializing every renderer argument is a useful experiment, but **not the selected production format**. Our prototype catches changed primary bytes and inconsistent reader projection, yet an internal result annotation changes the review digest and generated provenance comment despite identical reader prose. The experiment demonstrates a false invalidation cost. Do not install its full-input envelope as the canonical reader input.
- Copying the old runtime patch or building a universal new renderer/resolver is not authorized by the existence of B3.

## Bounded next work and stopping condition

The next implementation unit should first specify the supporting-source and provenance split above against actual Weekly and direct-primary callers, then change the shared reader input/renderer/Gate boundary together in an independent successor of f1. A projection-only patch must not be advertised as B3 closure. No need to reopen the successful B1/B2 maintenance review or run the interrupted broad suite merely for this design decision.

Required regression: each omitted reader field changes review identity and invalidates stale review; covered controls remain covered; current matching source passes; independently modified TeX plus refreshed manifest/report hashes fails creation and revalidation; wrong issue/Profile/route/explicit surface fails; direct-primary compatibility is demonstrated; internal audit-only mutations do not create unnecessary semantic-review work, while unauthorized output changes still fail; bibliography/citation/support boundaries are covered; missing/non-PASS semantic review prevents source materialization. Then exercise the repaired boundary through existing stage/revalidation wiring on a fixed candidate, followed by fresh independent implementation review. Broader diagnostics and canonical seven-point audit remain later acceptance requirements.

This unit ends at a tested design boundary, not a speculative production patch: the cheap full-input approach has a demonstrated cost defect, and supporting-source responsibilities are not yet justified well enough for implementation. B3 remains open. This is a root scope decision within the authorized review, not a request for renewed permission or an assertion that user input is required.
