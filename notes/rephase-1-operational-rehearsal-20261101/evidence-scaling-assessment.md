## 3. Alternatives (total-work objective, no automatic code)

What is UNKNOWN: full unmodified runtime (no fake full-runtime estimate — do not linearly extrapolate 228GB to completion as a guarantee; page-cache warmth, CPU card/validation cost beyond `task_source_ids`, accept/Views/ledger/completeness phases, timeout/OOM behaviour all unmeasured), physical disk cost (rchar ≠ disk proof), LLM/human review cost, recurring Weekly/Special cost. **(B) Small batch/subset route.**
Temp-only diagnostic (e.g., 5-task temp package or SP-13 path) can prove semantic equivalence of a repair vs unmodified where unmodified can finish, but **cannot silently drop needs or fake full Weekly**: `validate_interactive_input` 314–364 requires exact non-DROP coverage (409/409); any accepted subset would violate one-result-per-task + ledger exact-coverage + completeness universe U. **(C) Bounded private per-operation shared validated context + pure task resolution (recommended for repair-unit scoping).**
One full read validation at operation entry, pure per-task slices thereafter, appropriate final/revalidation boundary; standalone public calls still reload. No global/lifetime/epoch authority cache. See §4 for exact scope. This is the only alternative that keeps package-linear file reads where semantics are unchanged (≈425 reads per *package*, not per *task*) without inventing atomicity.
