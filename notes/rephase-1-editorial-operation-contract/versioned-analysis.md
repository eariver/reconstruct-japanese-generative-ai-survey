## 2. Why a versioned branch (and what it fixes vs the rejected correction)

Independent §9 still stands: the rejected correction (live in-place `temp+replace` + writer-internal QA generation + in-memory context + recipe-order fixture) leaves (a) archive-vs-changed-reader rederivation break, (b) self-generated QA validated against itself, (c) memory-only recovery authority, (d) `F0` self-reference. V answers each structurally, not by enlarging the same writer:

- (a) Archive break → V does NOT re-derive a changed reader from OLD authored bytes through the OLD canonical receipt. V defines a NEW strict versioned receipt route/variant (§5) whose inputs are explicitly (unchanged accepted upstream) + (actual proposed derivation from immutable proposed authoring/reader) + (render replay to versioned outputs) + (external reviews bound to the versioned set). The old receipt continues to validate the old canonical set unchanged; the new variant validates the new revision set. No 14th-write premise-copy.
- (b) Generated-PASS loop → V FORBIDS the operation from calling `build_review_record(..., PASS)` or equivalent to create semantic/visual authority. The two review judgments arrive as independent external persisted files (§8). The operation only validates them (`validate_review_record` ×2 with exact kind/check-family/page-count/fidelity + manuscript/source/pdf binding). Manuscript/bundle/gate/receipt deterministic builds remain allowed versioned-first because they are pure transforms of already-reviewed inputs, not review judgments.
- (c) Memory-only basis → V persists every decision input BEFORE the pointer commit: immutable preparation proof + versioned revision set + external reviews + expected before/predecessor/contract pins (all files, all SHA-bound). Crash before pointer commit leaves old authority healthy and the versioned set inert; crash during pointer commit uses the existing controller State-replace taxonomy (expected-old recheck + unknown-bytes preservation + manual recovery), never an in-memory intent log.
- (d) Fixture self-reference → V requires the fixture SOURCE + CONTRACT + accepted-authority fixture commit(s) to exist BEFORE any versioned authority file is created, and the versioned authority files are never part of the renderer basis (same rule as P3S S5 artifact-only HEAD compat). §11 fixes the exact order.

V costs explicit consumer edits (§4). That is the point: R1 already proved "unchanged consumers" infeasible, so V prices the change instead of hiding it.

### 4.1 New resolver (1 new module function, no new State field)

New module `scripts/survey_editorial_activation_v2.py` (proposed name; exact filename fixed at implementation):

```python
def resolve_active_publication_set(
    root: str | Path, cfg: dict[str, Any], state: dict[str, Any],
) -> dict[str, object]:
    # Returns {"mode": "CANONICAL" | "REVISED",
    #          "record_ref": {"path","sha256"} | None,
    #          "roles": {"reader-manuscript": {"path","sha256"}, "validated-source": ...,
    #                    "publication-pdf": ..., "quality-regression-bundle": ...,
    #                    "semantic-review": ..., "visual-review": ...,
```

Rules:

- `pointer = state.publication_revalidation_provenance`. If `None` → `CANONICAL` (initial route, today's behavior, byte-identical).
- Load record via existing `_load_revalidation_record` semantics (repo-local, symlink/missing/SHA/schema refusal). If `reason_class==REVIEWED_CORE_CHANGE` (old) or record has NO `editorial_bindings` → `CANONICAL`.

Any mismatch → fail-closed error, NEVER fallback to canonical.
- Mixed history: `supersedes` chain may mix both reason classes; chain walk stays reason-agnostic except membership (`REVIEWED_CORE_CHANGE | REVIEWED_EDITORIAL_CORRECTION`). Chronology/prior-checkpoint/issue rules unchanged (`_check_revalidation_chain:952-1017` + enum extension only).

## 6. Identity graph vs full replay (no State→Gate→receipt→State recursion)

- Identity graph (static, cheap, always): `State.pointer → activation record → editorial_bindings (proposal/retention/staged/scope SHAs + before/after digests) + active_role_refs (per-role {path,sha256}) → REVISION_README lineage`. - Acyclicity rules (schema-enforced): preparation proof schema has NO `record_ref` field; QA schemas (`reader-manuscript-v2 / quality-regression-bundle-v2 / publication-review-record-v2 / reader-surface-gate-v2 / longform-publication-source-manifest-v2`) gain NO record field; activation record schema ADDS `editorial_bindings + active_role_refs` (which reference preparation + revision QA, whose bytes already exist). Write order is `QA → receipt/gate → preparation-proof → activation record (O_EXCL) → State pointer (atomic replace)`. A manifest/receipt/review containing the hash of the record that contains it is unconstructible by construction (record hash computed LAST over already-frozen bytes).
- Backed by actual functions: graph = `core.repo_local_path/sha256_file/load_json + _load_revalidation_record + resolve_active_publication_revalidation + _check_immutable_rows/_check_chain`; replay = `validate_versioned_revision_receipt + validate_reader_surface_gate + validate_manuscript_manifest + validate_bundle + validate_review_record + validate_stage`.
