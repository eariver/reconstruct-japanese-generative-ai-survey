## 0. Question

After a COMMITTED Core implementation change on an ACTIVE versioned set (State pointer `publication_revalidation_provenance` selects a sealed `EDITORIAL_PUBLICATION_SET_V1`), what prior acceptance stays valid as history, what must rederive fresh for current eligibility, and what typed bridge closes the epoch gap — without (a) pretending old current-validators still pass, (b) silently weakening normal consumers, (c) forging a Core-change reason as editorial, or (d) rebinding a review target by equal SHA?

Definitions (no new trust framework, no authority cache):

- Historical identity: byte-pinned facts at a RECORDED commit (proposal/retention/staged/seal/Candidate/review bytes + `repository_commit_sha` + `code_deps`/`closure` rows + Git blobs). Proved by `git show <commit>:<path>` equality, never by live-file equality alone.
- Old execution replay: re-running OLD code bytes in isolation. Only considered as truly-pinned isolated replay under a NEW procedure (not saved runners); costs explicitly.
- Current eligibility: fresh in-invocation proof under NEW current code that the (old or renewed) set satisfies strict State + route rederivation + current closure/contract + healthy readback + normal consumer resolution. Historical validity never implies it.

## 3. Alternatives

### A. Same-contract reviewed implementation-only change → SELECT (bounded renewal operation)

Scope: toolchain/implementation bytes change WITHOUT schema/contract/route/toolchain-recipe change (same `pipeline_contract_version/sha`, same `CURRENT_CLOSURE` names/cardinality modulo explicitly reviewed additions, same P3S-50 shape or a mechanically reviewed expansion, same receipt/seal/record schemas, same lifecycle/gates).

Bridge (implementable; NEW procedure, not saved runners):

1. Historical verification under NEW current code WITHOUT executing old code: for the OLD active set, reload exact paths (proposal/retention/staged/seal/Candidate/reviews/build), re-verify P2R retained bytes (`verify_retention`), re-verify L seal cross-bindings (`validate_seal`) and activation history (`verify_activation_history`, historical only), and verify OLD `current_tools`/`code_deps` rows against OLD commit blobs via `git show <old_commit>:<path>` (pattern: `verify_closure_at_commit`). This proves historical identity, not eligibility.
2. Truly-pinned old-code isolated replay ONLY if needed to prove the old PDF was deterministically replayable at its epoch (e.g., disputed `REPLAY_MISMATCH` root-cause): fresh isolated worktree/index at OLD commit, file-selected 50 + trio + schemas only, disposable build root, fixed recipe, no network, no saved runner reuse, no reconstruct-DB objects. Costed separately; NOT the default path. Default renewal does NOT re-execute old code.
3. New derivation under NEW code: from explicit paths + OLD State bytes + OLD set + NEW current code (never caller skip-flag), re-derive route context on the SAME accepted research (`accepted_refs` FULL equality, archive path+SHA), re-render main/bib, re-`validate_generated_closure` with NEW style bytes, rebuild PDF in disposable root with NEW toolchain (new `build-record.json`), re-verify P3S with NEW `code_deps` (new pins), mint NEW receipt (`EDITORIAL_PUBLICATION_SOURCE_V1` with NEW `current_tools`/closure/contract/commit) + NEW manuscript/QA/Gate/Candidate + NEW seal (`SEALED_INERT`) + NEW activation record on a NEW typed renewal branch (see §4), then State-pointer swap with full §7 failure/resume semantics.
4. Reviews: same-reader/same-source-PDF (bit-identical PDF) → exact-path review reuse is the ONLY reuse allowed (other Worker owns exact rule); same-reader/changed-output (any PDF/source byte change, including style/toolchain-rendered drift) → REQUIRED new postrender semantic + visual + deterministic QA at final paths (no same-SHA target copy, no retrospective PASS).

Costs: versioned storage (prior immutable set KEEP), full revalidation (P1/P2R/P2V/P3S/H + normal consumers), explicit resume, operator attempts, implementation/test time. Saves: no canonical overwrite/rollback across review wait, no stale Candidate swap, no duplicate reader/staged copies (same as R3).

### B. Arbitrary schema/contract/toolchain migration → REFUSE in this unit (separate contract required)

Triggers: `contract_files`/`pipeline_contract_version` change, `CURRENT_CLOSURE` name/cardinality change beyond reviewed expansion, schema shape change (new required keys, `additionalProperties` relaxation, new receipt/seal kinds), route semantics change, toolchain recipe change, profile/role rebinding, research/Architecture/Draft authority change, accepted-upstream (DM022) change.

Disposition: refuse renewal under the same-contract operation BEFORE writes (exact blocker, not reason-only prose). A migration needs a NEW contract decision + new schemas/closures + new fixture chain (meaningful source commit BEFORE authorities, per d880 §14) + fresh independent review + fixed-candidate/audit impact. Silently widening `CODE_DEPS`/`CLOSURE_SET`, caching an old contract, or mapping old closure names to new paths by directory prefix would be a blanket-ignore bypass — forbidden. If the epoch gap cannot be closed within same-contract scope, the correct output is the named blocker (e.g., `CONTRACT_MISMATCH: pipeline_contract_sha X != Y`, `CLOSURE_SET: missing=[…] extra=[…]`, `CODE_DEPS_EXPANSION_REQUIRED: […]`) plus a root decision to open a migration contract — NOT a reason-only plan that pretends feasibility.

### C. Non-alternatives (explicitly rejected)

- Re-bless old pins by editing expected closures to match old bytes (breaks `_verify_head_bytes` control-root guarantee; forges current eligibility).
- Execute old code live against new State (conflates historical replay with current authority; `RUNTIME_BINDING` tripwire exists to refuse this).
- Mint `REVIEWED_CORE_CHANGE` for a versioned renewal (implies canonical replacement; breaks active projection + KEEP/COPY semantics) or mint `REVIEWED_EDITORIAL_CORRECTION` with a false editorial reason for a Core change (contract §10 + assessment §5.3 forbid; R1/canonical refusal would be bypassed).
- Reuse reviews by copying a same-SHA file to a new review path (seal/high review-TARGET binding forbids; `CANDIDATE_INVALID … manuscript drift` precedent in R6 crossbind).
- `ALREADY_ACTIVE` as renewal success (read-only, no mutation) or orphan-record adoption without explicit `resume_activation` full revalidation.

## 5. Failure / resume / quota / genuine-approval boundaries (renewal inherits §7)

- `prepare` incomplete (build failure, extra input/output/hash drift, toolchain/spec mismatch) → old State healthy, incomplete publication dir inert/preserved, new proposal ID for retry (no same-byte takeover, no auto-cleanup).
- Seal complete before activation → explicit activation retry with FULL current-before + full set revalidation (seal is not permission).
- Record created, State still exact old → `resume_activation` ONLY on explicit orphan path with full current-before/set/record-intent revalidation; ordinary `activate` refuses collision (`RECORD_COLLISION`/`INTENT_COLLISION`).
- State already exact expected new → `ALREADY_ACTIVE` read-only (strict active State + full set, no takeover, no fresh approval).
- State neither known-old nor expected-new / unreadable / unsafe → `INDETERMINATE`, preserve all bytes, no overwrite/rollback/adoption.
